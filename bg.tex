\subsection{Power Glitching}

\noindent\textbf{Scope: power (voltage) glitching.}
This proposal focuses on \emph{power (voltage) glitching}, in which the attacker briefly perturbs the supply voltage of a target to induce computational faults (e.g., instruction skips and corrupted data).
We deliberately set aside \emph{clock glitching}, which was historically a primary fault-injection vector but is largely ineffective against contemporary embedded systems: modern embedded devices increasingly run from internal PLLs and on-chip oscillators rather than an externally supplied clock, and many integrate clock-integrity and frequency monitors, so externally injected clock glitches are filtered out or detected \TODO{cite clock-glitching countermeasures / internal-clock trend}.
Voltage glitching, by contrast, targets the power rail directly, requires only low-cost equipment, and remains broadly effective across current embedded targets \TODO{cite recent voltage-glitching attacks}, making it the most relevant and impactful vector to study and defend.

\noindent\textbf{How power glitching works, and how we mount it.}
A power glitch momentarily perturbs the target's supply voltage so that, for a brief window, logic gates miss their timing and the processor mis-executes: an instruction is skipped, an instruction or operand is corrupted, or a memory access returns the wrong value~\cite{oflynn2016crowbar}.
The dominant low-cost technique is the \emph{crowbar} glitch, in which a power MOSFET briefly shorts the supply rail to ground to produce a fast, precisely timed voltage dip rather than a smoothly shaped waveform~\cite{oflynn2016crowbar}.
We mount these attacks with the open-source ChipWhisperer platform~\cite{chipwhisperer, chipwhispererdocs}, the de facto standard for fault-injection research, which generates crowbar glitches synchronized to the target's own clock.
A glitch is described by a small set of parameters: its \emph{width} (how long the rail is shorted), its \emph{offset} (the phase within the targeted clock cycle), an \emph{external offset} (the number of cycles after a trigger at which the glitch fires), and a \emph{repeat} count (how many consecutive cycles are glitched), with separate high-power and low-power crowbar transistors for different targets.
Because only a small, target-specific region of this parameter space produces an exploitable fault, an attack campaign searches over these parameters and classifies each trial as normal, crash or reset, or a successful fault~\cite{chipwhispererdocs}.
Canonical demonstrations include skipping iterations of a counting loop, bypassing password or authentication comparisons, and defeating secure-boot checks~\TODO{cite concrete examples, including our own eCTF exploits}.

\subsection{A Motivating Example: Compiler Optimization Reshapes the Attack Surface}
\label{sec:motivating}

A central observation of this proposal is that the susceptibility of a security check to glitching is not a property of the source code alone, but of the machine code the compiler emits for it.
Consider the bounded-output routine \texttt{write\_bytes} in Figure~\ref{fig:motivating}(a), a representative pattern found across embedded firmware: a length-bounded loop that emits exactly \texttt{len} bytes from a buffer and periodically awaits an acknowledgment.
The same shape, ``iterate up to a length bound while transmitting or computing,'' underlies firmware-image transmission, secure-boot manifest emission, and bounded buffer copies, so the safety property ``no more than \texttt{len} bytes leave the device'' is security-critical.
Compiled by \texttt{arm-none-eabi-gcc} from identical source at two standard optimization levels (\texttt{-Os} for size and \texttt{-O2} for speed), the same function yields qualitatively different machine code with dramatically different exposure to a single-instruction skip.

\begin{figure}[t]
\centering
\begin{minipage}[t]{\linewidth}
\centering{\scriptsize\textbf{(a) C source of \texttt{write\_bytes}.} Identical source is fed to \texttt{arm-none-eabi-gcc} at the two optimization levels shown below.}
\begin{lstlisting}[language=C, basicstyle=\footnotesize\ttfamily, numbers=left, numberstyle=\tiny, frame=single, framesep=2pt]
int write_bytes(const void *buf, uint16_t len, bool ack) {
    for (int i = 0; i < len; i++) {
        if (i % 256 == 0 && i != 0) {           // expect an ACK every 256 bytes
            if (ack && read_ack() < 0) return -1;
        }
        putch(((uint8_t *)buf)[i]);
    }
    return 0;
}
\end{lstlisting}
\end{minipage}

\vspace{0.4em}
\begin{minipage}[t]{0.48\linewidth}
\centering{\scriptsize\textbf{(b) Thumb assembly at \texttt{-Os} (size). Top-tested loop: \texttt{cmp/bgt} guards the body.}}
\begin{lstlisting}[style=armasm]
head:                ; loop head
  cmp   r5, r4       ; r5=len, r4=i
|\glitchhl{~~\textbf{\textcolor{blue!60!black}{bgt}}~~~body~~~~~~~~~;~\textcolor{red!70!black}{\textless==~skip~=\textgreater~+1~byte}}|
  movs  r0, #0       ; return 0
  pop   {r3..r7,pc}  ; exit
body:
  uxtb  r3, r4
  cbnz  r3, emit     ; ACK gating
  cbz   r4, emit
  cbz   r7, emit
  bl    read_ack
emit:
  ldrb  r0, [r6,r4]  ; putch(buf[i])
  bl    putch
  adds  r4, #1       ; ++i
  b     head         ; back to head
\end{lstlisting}
\end{minipage}\hfill
\begin{minipage}[t]{0.48\linewidth}
\centering{\scriptsize\textbf{(c) Thumb assembly at \texttt{-O2} (speed). Body-first loop: \texttt{cmp/beq} exits only on \emph{equality}.}}
\begin{lstlisting}[style=armasm]
body:                ; loop body
  adds   r4, #1      ; ++i
  ldrb.w r0,[r5,#1]! ; load buf[i]
  bl     putch
  cmp    r4, r6      ; i == len ?
  uxtb   r3, r4
|\glitchhl{~~\textbf{\textcolor{blue!60!black}{beq}}~~~~exit~~~~~~~~;~\textcolor{red!70!black}{\textless==~skip~=\textgreater~unbounded}}|
  cmp    r3, #0      ; ACK gating
  bne    body
  cmp    r7, #0
  beq    body
  bl     read_ack
  b      body
exit:
  movs   r0, #0      ; return 0
  pop    {r3..r7,pc}
\end{lstlisting}
\end{minipage}
\caption{The same \texttt{write\_bytes} routine compiled at \texttt{-Os} versus \texttt{-O2} with \texttt{arm-none-eabi-gcc}. The \texttt{-Os} variant (b) keeps a top-tested loop (\texttt{cmp r5,r4} then \texttt{bgt}); a single-skip glitch yields at most one extra byte, so an $m$-byte overread requires $m$ successful skips ($P_{\text{attack}}\!\approx\! p^m$). The \texttt{-O2} variant (c) restructures the loop body-first with an equality termination (\texttt{cmp r4,r6} then \texttt{beq}); skipping the comparison at the unique boundary iteration makes the equality test never trigger again, yielding an unbounded overread from a single fault ($P_{\text{attack}}\!\approx\! p$).}
\label{fig:motivating}
\end{figure}

With the two compiled variants placed side by side, the contrast is stark.
At \texttt{-Os} (Figure~\ref{fig:motivating}(b)), the loop terminates via a greater-than test against the length bound; a single skip near the boundary at most lets one extra byte through before the next iteration's comparison succeeds and the loop exits, so attaining an $m$-byte overread requires $m$ independent successful skips and the attack probability behaves as $P_{\text{attack}}\!\approx\! p^m$.
At \texttt{-O2} (Figure~\ref{fig:motivating}(c)), the same source becomes a body-first loop that terminates only on \emph{equality} of the index and the bound; if the attacker skips the comparison at the unique iteration where index equals bound, every subsequent comparison fails because the index runs past the bound, and the loop continues until external resources are exhausted, yielding an unbounded overread from a single fault with $P_{\text{attack}}\!\approx\! p$.
The exploitable surface collapses from ``each successful skip costs one extra byte'' to ``one successful skip costs every remaining byte,'' so the same source becomes drastically more glitchable simply because the developer asked the compiler to optimize for speed rather than size.
We have empirically confirmed this asymmetry on a Cortex-M4 target with ChipWhisperer voltage glitching across 100{,}000-trial campaigns~\TODO{cite the in-prep compiler-glitch paper}, the experimental backbone of the PI's preliminary work that this proposal builds on.
The example motivates Thrust~1, which characterizes and quantifies how compiler transformations like these reshape the glitching attack surface along two axes, the size of the exploitable schedule $|\sigma|$ and the magnitude of the resulting violation, and it foreshadows Thrust~3, where we turn the same compiler into the place to reduce that surface.

\section{System and Threat Models}

\noindent\textbf{System model.}
We target embedded and IoT systems, representatively single-core ARM Cortex-M class devices \TODO{confirm target families/boards}, whose firmware is produced by a standard optimizing compiler toolchain (e.g., LLVM/GCC).
The software stack includes security-critical decision points such as secure-boot signature checks, firmware-update authentication, debug/lifecycle locks, and access-control or PIN/password comparisons, as well as the cryptographic routines that protect device secrets.
The assets to be protected are the integrity of these control-flow decisions and the confidentiality and integrity of on-device secrets (e.g., keys).
We assume the underlying hardware behaves correctly in the absence of an induced fault; the compiler and the hardening it applies (Thrust~3) are part of the trusted computing base.

\noindent\textbf{Threat model.}
The adversary has physical or close-proximity access to the target and can mount \emph{power (voltage) glitching} (see the scope discussion above): by briefly perturbing the supply voltage, the attacker induces transient faults that we model as \emph{instruction skip}, \emph{instruction corruption}, and \emph{data corruption} affecting a bounded number of instructions/cycles per injection \TODO{state the precise fault model adopted, defined formally in Thrust~2}.
The attacker can repeat injections and tune their timing/parameters across many attempts, and observes the device's externally visible behavior to confirm success.
The adversary's goal is to subvert a security-critical decision, for example to skip an authentication or secure-boot check, force an unintended branch, or corrupt data to leak or alter secrets.
\noindent\textbf{Out of scope.}
We do not consider invasive attacks (decapsulation, focused ion beam, microprobing), purely software-only exploitation, or side-channel leakage, which are complementary and addressed by a large separate literature.
Consistent with our scope (above), clock glitching is excluded as it is no longer effective against modern embedded systems; EMFI and laser fault injection are \TODO{out of scope or future work: state which and why}.
We make no claim of \emph{eliminating} fault-injection attacks: a determined adversary with unbounded attempts can always induce some fault. \sysname instead \emph{reduces} the exploitable attack surface and provides resistance guarantees under an explicitly \emph{bounded} fault model.
